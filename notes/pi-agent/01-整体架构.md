# 第 1 章：Pi 整体架构与源码阅读法

## 学习目标

读完后，你应该能解释为什么 Pi 分为 `pi-ai`、`pi-agent-core`、`pi-coding-agent` 等层，知道一条用户输入经过哪些边界，并能从一个公开 API 反向找到实现。

## 1. 先把名字拆开

“Pi”通常指终端编码助手这个产品，也可能指整个 monorepo。monorepo 里其实有多个可独立复用的 package：

```text
用户 / 程序
   │
   ├── CLI / Interactive / JSON / RPC / SDK       packages/coding-agent
   │                 │
   │                 ├── Session、资源、工具、扩展
   │                 └── Agent + streamFn          packages/agent
   │                                                │
   └────────────────────────────────────────────────┼── Models / Provider / API  packages/ai
                                                    └── TUI                 packages/tui
```

MCP、Codemode、Telemetry 和 Durable/Chord/Env 是可复用或并行的能力，并不都必须经过交互式 coding-agent。尤其 `pi-durable` 是另一个持久化 harness；它不是普通 CLI session 的内部实现。

## 2. 一条实际请求

用户说“找出配置里的超时并告诉我”。典型轨迹是：

1. `coding-agent` 收到编辑器输入，组装 system prompt、活动分支、模型和工具定义。
2. `agent-core` 将请求交给 `streamFn`，把 provider 的文本/工具调用增量转成 Agent 事件。
3. 模型返回 `read({path: "config.json"})` 这样的 tool call。
4. Agent 校验参数并执行 read tool，将 tool result 追加到对话上下文。
5. Agent 再调用模型，模型把找到的值说给用户。
6. SessionManager 将新增消息写入 JSONL；InteractiveMode 订阅事件并刷新 TUI。

```text
输入 → context + tools → provider stream → assistant(toolCall)
     → validate → execute(read) → toolResult → provider stream → final text
     → append session entries → render
```

这条路径的边界是核心设计：模型适配不负责文件 I/O；Agent 不负责终端布局；TUI 不负责组 prompt；SessionManager 不决定模型如何生成。

## 3. 如何从 API 找回源码

用四步读法：

1. 从 package 的 `README.md` 找使用例子和抽象词汇。
2. 从 `package.json` 的 `exports` 找正式入口，不能假设 `src/index.ts` 暴露所有文件。
3. 从入口的导出反向找实现，例如 `Agent.prompt()` → `agent.ts` → `agent-loop.ts`。
4. 同时读该路径的测试：测试通常说明时序、边界和错误行为，比名称更精确。

例：要追踪 provider 事件，可以从 [pi-ai 的类型](../../pi/packages/ai/src/types.ts) 找 `AssistantMessageEventStream`，再看 `api/*.ts` 的 provider 适配，最后看 [event-stream.ts](../../pi/packages/ai/src/utils/event-stream.ts) 如何承载事件。

## 4. 三种不要混淆的“上下文”

| 名称 | 含义 | 示例 |
|---|---|---|
| Agent context | 当前 Agent 内存态，含消息、工具、system prompt 等 | 一次运行中的 `AgentContext` |
| Model context | 发给 LLM 的合法消息序列 | system/user/assistant/toolResult |
| Session context | 从当前 session 分支投影出的可恢复状态 | JSONL 中当前 leaf 的历史 |

例如，UI-only 的状态消息可以留在 Agent 或 session 中，但由 `convertToLlm()` 过滤；它不会因此自动进入 provider 请求。

## 5. 两个 harness 的心智模型

普通 coding-agent 的中心是“会话 + Agent loop”：先产生一个模型响应，再按调度继续；历史写入本地 JSONL。`pi-durable` 的中心是“提交 + 持久任务”：模型生成和每个工具调用都是可恢复 task，操作先提交，完成后再可见。

```text
普通 Pi：prompt → agent loop → tool → append session
Durable：submit → commit input → generation task → tool task → commit output
```

例：进程在 `bash` 执行一半时退出，普通 Pi 的 session 留下已写入的记录，恢复策略由 coding-agent 管理；Durable 会依据工具的 replay policy 决定重跑或写入 interrupted 结果。两者解决的问题相近，但持久化保证不同。

## 6. 阅读练习

打开 [coding-agent 的 how-pi-works](../../pi/packages/coding-agent/docs/how-pi-works.md)，用五个方框画出输入、请求组装、LLM、tool execution、存储/呈现。然后从 [agent-loop.ts](../../pi/packages/agent/src/agent-loop.ts) 找到你预测的“工具结果后又请求模型”的循环位置。

## 本章小结

Pi 不是一个巨大的单体 agent 函数，而是若干具有清晰边界的包。理解边界之后，继续学习时要追踪“数据类型如何跨边界”以及“状态由哪一层拥有”。
