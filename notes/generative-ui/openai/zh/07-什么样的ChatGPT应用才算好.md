# 什么样的 ChatGPT 应用才算出色

> 完整的文档索引请参阅 [llms.txt](/llms.txt)。在页面 URL 末尾追加 `.md` 即可获取对应文档页面的 Markdown 版本。

在 DevDay 上，我们发布了 [ChatGPT Apps](https://openai.com/index/introducing-apps-in-chatgpt/)——一种把你的产品直接带进 ChatGPT 对话的全新方式。本文将在此基础上，为开发者、产品经理和设计师提供实用指导，帮助你们选对用例，并设计出上线之后真正有用的应用。我们会重点探讨如何把产品自身的优势转化为清晰、边界明确的能力，让模型能够在各种不同的对话和用户意图中加以运用。如果你想直接查看原始的技术工作流，可以跳转到 [Apps SDK quickstart](https://developers.openai.com/plugins/build/app-quickstart) 和 [developer docs](https://developers.openai.com/plugins)。

我们将涵盖：

- ChatGPT 应用究竟是什么（以及不是什么）
- 应用能够真正创造价值的三种方式
- 如何为对话和发现而设计
- 如何判断你的应用是否真的在发挥作用
- 具体示例与截图建议

## ChatGPT 应用究竟是什么

团队在构建第一个 ChatGPT 应用时，出发点往往是：

&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;&nbsp;_“我们已经有一个产品了，把它带进 ChatGPT 吧。”_

这通常始于把现有的 Web 或移动端体验——页面、菜单、流程——改造成适合聊天的形态。这是一种很自然的直觉；多年来，“软件”就意味着页面、导航和 UI 骨架。

然而，为 ChatGPT 构建应用是一个截然不同的环境。用户并不是在“打开”你的应用然后从首页开始浏览。他们正在就某件事进行对话，而模型可以决定何时把应用引入这场对话。用户是在某个时间点切入的。
在这个世界里，最优秀的应用从外部看往往出奇地“小”。它们不会试图复刻整个产品，而是让用户在 ChatGPT 中使用应用时，能够调用少数几种**特定的能力**：也就是你的产品最擅长、且模型可以在任何对话中复用的那些具体能力。

在 ChatGPT 之外，你的应用往往就是目的地。用户会：

1. 点击你的图标
2. 进入你的环境
3. 学习你的导航和 UI 模式

大多数产品决策都源于这样一个假设：“屏幕是我们的。”你可以在布局、新手引导（onboarding）和信息架构上大量投入，因为用户已经投入到了你的空间里。

而在 ChatGPT 内部，你的应用扮演着不同的角色：

- 它是模型可以调用的一种**能力**（capability）\- 既用于提供上下文，也用于视觉上的呈现与互动。
- 它出现在**进行中的对话内部**。
- 它只是模型可能编排的多个工具之一。

这意味着“价值单元”与其说是你的整体体验，不如说是你能在恰当的时机帮助模型和用户完成的具体事情。

一个实用的定义：

**ChatGPT 应用是一组定义清晰的工具，能够执行任务、触发交互或访问数据。**

这带来了几点推论：

- 你不需要移植每一个功能。
- 你不需要完整的导航层级。
- 但你_确实_需要一套清晰、紧凑的 API：一组易于调用、易于在其上继续构建的操作。

你可以这样理解：你的 ChatGPT 应用是一个工具箱，当用户遇到某种特定类型的问题时，模型就会伸手去取它。这个工具箱定义得越精确，就越容易在对话流程中自如使用。

一旦你把应用视为“模型可以编排的能力”，而不是“我们产品的迷你版”，设计决策就会清晰很多。你开始问“在这里我们能帮上什么忙？”，而不是“用户接下来应该去哪里？”

## 创造真正价值的三种方式

对于任何应用创意，都可以用一组简单的标准来过滤：

- **Know（知晓）：** 它是否让用户能够使用原本在 ChatGPT 中看不到的新上下文或新数据？
- **Do（行动）：** 应用是否代表用户执行真实的操作？
- **Show（展示）：** 应用是否以比纯文本更清晰、更易于操作的 UI 呈现信息？

这条标准既适用于**“严肃”**的效率类应用，也适用于游戏这类**“纯属娱乐”**的应用。游戏或许无法帮人更快完成一份报告，但它依然在做基础模型自身做不好的事情：维护有状态的游戏逻辑、追踪进度、执行规则，或者渲染游戏世界中有趣的视图。它的价值在于愉悦感和参与度，但底层的模式是一样的。

### 1\) 值得知晓的新内容

你的应用让新的上下文在 ChatGPT 对话中可用：

- 实时价格、库存与可用性
- 内部指标、日志、分析数据
- 专属的、需要订阅的或小众的数据集
- 用户专属数据（账户、历史记录、偏好、权益）
- 传感器数据、实时视频流

实践中，这往往意味着打通那些数据准确、实时且经过权限控制的系统。应用成为模型在你的领域中的“眼睛和耳朵”，从而能够更有权威性地回答问题。

### 2\) 可以_动手去做_的新操作

你的应用代表用户执行操作：

- 在内部工具中创建或更新记录
- 发送消息、工单、审批和通知
- 安排日程、预订、下单或进行配置
- 触发工作流（部署、升级处理、同步数据）
- 运行交互式游戏（执行规则、推进回合、追踪状态）
- 在物理世界中执行操作（IoT、机器人控制等）

在这里，应用与其说是“事实来源”，不如说是一双“手”。它把用户的意图转化为团队日常使用的系统中的具体变更——或者就游戏而言，转化为游戏状态的具体变化，让体验保持一致与公平。这正是你的应用以有意义的方式转变为 agent（智能体）的地方。

### 3\) 更出色的展示方式

应用可以在 ChatGPT 对话中以 GUI 的形式呈现信息，让信息更易于理解或更易于操作：

- 精选清单、对比、排名
- 表格、时间线、图表
- 面向特定角色或特定决策的摘要
- 游戏状态的可视化或结构化视图（棋盘、物品栏、分数）

当用户正在做选择或权衡时，这一点尤其有价值。应用可以为模型提供一种“结构化的语言”：带有列、行、分数的组件（widget），以及符合人们实际决策方式的可视化——或者在游戏中，帮助玩家理解自己“身处何处”的画面。

如果一个应用没有在 **know/do/show** 中的至少一项上带来明显提升，它往往会让人觉得没有在 ChatGPT 已有能力之外增加价值。用户可能不会明确抱怨，但无论这个应用是用来工作还是娱乐，这都是一个错失的机会——错失了为用户提供更有意义价值的机会。

## 选择能力，而不是移植你的产品

一个常见的第一反应是列出产品的所有功能，然后问：“我们怎么把这些功能搬进 ChatGPT？”

纸面上看，这想法很周全。但在实践中，它通常会造就一个庞大而模糊的功能面，模型难以驾驭，用户也难以理解。如果你很难用一句话概括这个应用是做什么的，模型理解起来同样会更加吃力。

更有效的路径是：

1. **列出核心任务（jobs-to-be-done）\-** 识别用户想借助你的产品完成的具体任务或目标。这些正是你的产品存在的根本理由。从这里出发，能让你始终围绕用户成果，而不是陷入功能清单。  
    例如：
   - 帮助用户挑选一套房子。
   - 把创意转化为精美的演示文稿。
   - 将意图转化为令人愉悦的探索体验。
   - 把原始数据变成清晰、可分享的报告。

2. 针对每一项任务，问自己：

   “如果没有应用，用户在 ChatGPT 对话中做不到什么？”

   常见的答案包括：
   - 访问实时或私有数据。
   - 在我们的系统中执行真实操作。
   - 获得用户所需的结构化或可视化输出。

3. 你的独特价值就在这里开始显现。此时你思考的不再是“我们在技术上能暴露什么？”，而是“我们在哪些方面能提供独一无二的帮助？”

4. 把这些差距转化为少量**命名清晰的操作（operations）**。例如：
   - `search_properties` – 返回候选房源的结构化列表。
   - `explain_metric_change` – 获取相关数据并总结可能的原因。
   - `generate_campaign_variants` – 创建多个带元数据的广告变体。
   - `create_support_ticket` – 创建工单并返回摘要 \+ 链接。

这些操作具备以下特点：

- 足够具体，模型能自信地选用
- 足够简单，能在对话中与其他步骤灵活组合
- 直接与价值挂钩，而不是覆盖你整张产品地图

换一个角度思考：如果团队里有人问“这个应用必须做好哪三件事？”，那么答案几乎应该与你的产品能力一一对应。

## 为对话与发现而设计

在 MCP server 中，你可以定义 [`description`](https://developers.openai.com/plugins/reference#component-resource-_meta-fields)，为模型提供上下文，说明何时调用你的工具，以及具体执行哪些工具调用来完成特定任务。这有助于把用户意图映射到你的工具操作上。

### a) 意图模糊

> 帮我想想该住在哪儿。

一个良好的应用响应应该：

- 利用对话中已有的相关上下文。
- 必要时最多问一两个澄清性问题。
- 快速产出具体的内容——例如，给出几个示例城市并附上简短说明。

用户应该感觉到进展已经启动，而不是被丢进一个多步骤的引导流程。如果他们必须先回答五个问题才能看到有用的东西，很多人会直接放弃。

> 在西雅图找 120 万美元以下、口碑好的小学附近的三居室房源。

此时，应用不应该让用户重复表达。它应该：

- 解析查询。
- 调用合适的能力。
- 返回一组聚焦且结构良好的结果。

你仍然可以提供细化选项（“你更在意通勤还是学校评分？”），但这些应该像是可选的微调，而不是必填的设置。

### c) 没有品牌认知

你不能假设用户知道你是谁。

你的第一条有实质内容的响应应该：

- 用一句话说明应用的角色（“我负责抓取实时房源和学校评分，方便你比较各个选项。”）
- 立刻给出有用的输出。
- 提供一个清晰的下一步（“让我按通勤、社区或预算来帮你筛选。”）

把它当作一个冷启动问题：你要在一两条消息之内介绍清楚你_是_什么、你_为什么_有用，以及_如何_使用你。

## 为模型和用户同时设计

你的设计面向两类受众：

- 对话中的人类用户
- 决定何时以及如何调用你的应用的模型运行时（model runtime）

大多数团队对第一类思考得很充分，第二类则相对陌生。但如果模型无法理解你的应用做什么、怎么用，那么面向用户的体验也就没多少机会真正跑起来。

还有第三个同样重要的维度：**模型调用你的应用时，有哪些用户数据会流经其中。** 良好的应用设计不只是能力清晰，还在于严格自律地对待请求_什么_数据以及_如何_使用这些数据。

- **清晰、具描述性的操作与参数：** 让模型一眼就能看出你的应用何时相关、如何调用。使用直白的名称（`search_jobs`、`get_rate_quote`、`create_ticket`），并明确说明哪些参数（params）是必填的、哪些是可选的，以及它们的格式。任何含糊之处都会给路由（routing）增加成本。

- **隐私内建于设计（privacy by design）：** 只要求真正需要的字段。避免那种把额外上下文一网打尽的“大杂烩”（blob）参数。优先采用最小化、结构化的输入，不要使用“直接把整段对话发过来”之类的指令。

- **可预测、结构化的输出：** 保持 schema 稳定；包含 ID 和清晰的字段名。把简短的摘要（“三个符合你预算和通勤时间的选项”）与机器友好的列表（`[{id, address, price, commute_minutes, school_rating, url}, …]`）配对提供。这样模型既能自然地与人交流，又能精确地把控数据。

- **对_不_返回的内容要有取舍：** 不要“以防万一”地把敏感内部信息一并返回。确保 token/密钥不出现在用户可见的路径中。当不需要完整精度时，进行脱敏或聚合处理。

- **明确说明你收集什么以及为什么：** 只请求完成任务所需的最少信息。当需要敏感信息（例如账号访问权限）时，用一句话说明原因。设计操作和 schema 时，要让什么数据被发送到哪里一目了然。

## 为生态系统而设计，而非围墙花园

在真实的 ChatGPT 会话中，你的应用很少是唯一登场的角色。模型可能会在同一场对话中调用多个应用。

从用户的角度看，这是一条连贯的流程。从你的角度看，这是一个提醒：你是生态系统的一部分，而不是一个封闭的产品。

由此带来几个实际的启示：

- 保持操作**小而聚焦**
  - 比如 `search_candidates`、`score_candidates`、`send_outreach`
  - 而不是单个 `run_full_recruiting_pipeline`。

- 让输出**易于传递**
  - 稳定的 ID、清晰的字段名、一致的结构。
  - 避免把重要信息只藏在自由格式的文本里。

- 避免冗长的、隧道式的流程
  - 做好你自己的那部分工作，然后把控制权交还给对话。
  - 让模型决定下一步该由哪个工具来处理。

如果其他应用（或你自己应用的未来版本）能够轻松地基于你的输出进行构建，你就能从生态系统中其他环节的改进中获益，而不是与它们竞争。

## 一份快速检查清单

一份你可以在构建前后对照使用的简短清单：

- [ ] **1. 新的能力**
  - [ ] 你的应用是否能明确地知晓、执行或展示新的事物？
  - [ ] 如果它停止工作，目标场景中的用户会察觉到吗？

- [ ] **2. 聚焦的能力面**
  - [ ] 你是否选择了一小部分能力，而不是克隆整个产品？
  - [ ] 这些能力的命名和范围界定是否能清晰地对应真实的任务（jobs-to-be-done）？

- [ ] **3. 首次交互**
  - [ ] 你的应用是否能优雅地处理模糊和具体的提示（prompt）？
  - [ ] 新用户能否从第一次有意义的响应中理解你的角色？
  - [ ] 他们是否在第一轮就看到了价值？

- [ ] **4. 对模型友好**
  - [ ] 操作和参数是否清晰、无歧义？
  - [ ] 输出是否足够结构化和一致，以便进行链式调用和复用？

- [ ] **5. 评估**
  - [ ] 你是否有一个小而精心设计的测试集，涵盖正向、负向和边界用例？
  - [ ] 你是否大致了解应用给出的答案相对于没有应用时 ChatGPT 答案的胜率？

- [ ] **6. 生态契合度**
  - [ ] 其他应用和用户能否合理地基于你的输出进行构建？
  - [ ] 你是否乐于成为多应用链条中的一环，而不是包办整个旅程？

你不必在每个维度上都做到完美才能发布。但如果对其中大多数问题你都能回答"是"，那么你不只是把产品放进了 ChatGPT，而是让 ChatGPT 在你的领域获得了真正的杠杆（leverage）——这正是这类应用开始变得不可或缺的地方。
